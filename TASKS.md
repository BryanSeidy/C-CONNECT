### Design decision — resolved (2026-07-04)

The delivered logo's icon colors (mint green `#46F78D`, blue `#0298C6`, yellow `#F4EF47`) did not match `Brand_Identity_Guidelines.md`. Resolved by recoloring the mark rather than amending the guidelines: the geometry is untouched (same four quadrant arcs + wedge, same shading/bevel), only hue was remapped via HSV so the original anti-aliasing and depth are preserved. Final: top-left/bottom-left arcs Secondary Green `#406A5A`, top-right/bottom-right arcs Primary Green `#13352E`, wedge and wordmark use Gold `#D9A441` and Primary Green respectively — the wedge recoloring actually restores the guidelines' own "golden connection node" spec, which the original PNG hadn't matched. No blue or yellow remain anywhere in the mark. Documented in `DESIGN_SYSTEM.md` → "Logo & Brand Mark System".

## Completed — Critical bug fixes & lint/type debt (2026-07-08)

- [x] **Critical bug (backend, found this session):** `users` table was missing `name`, `fullName`, `companyName`, `country`, `isVerified` columns that `AuthController::register`, `RfqController`, `DisputeController`, and `RecurringOrderController` all read/write — meaning **every registration attempt would throw a fatal SQL error**. **Update:** the repo owner independently pushed a schema-first fix in the same window (commit `64850c1`) — `User` model now uses real `nom`/`prenom` columns plus a `getFullNameAttribute()` accessor, and `companyName`/`country`/`isVerified` were dropped from `$fillable` entirely (they never mapped to a real column; company name/region live on `SellerProfile`/`Company`). Rebased onto that fix and dropped the now-redundant migration this session had drafted. **Follow-on found:** `RfqController`, `DisputeController`, `RecurringOrderController`, and the new `NegotiationController` all still restricted their eager-loads to `id,fullName,companyName[,country]` — non-existent real columns — which would still crash every RFQ/Dispute/Recurring/Negotiation list endpoint even after the registration fix. Changed all of these to select `id,nom,prenom` (the accessor then computes `fullName` in the JSON response as before); `companyName`/`country` are simply absent from these responses now — frontend already falls back to `fullName` where it displayed `companyName`, so this degrades gracefully rather than crashing. If a real "company name" is wanted on these lists, it should come from `seller.businessName` (already eager-loaded) rather than a user column.
- [x] **Critical bug (backend, found this session):** `product_id`/`order_id`/`category_id` validation rules used `'uuid'` in `OrderController`, `RecurringOrderController`, `RfqController`, `DisputeController`, and `PaymentWebhookController`, but these are all `bigIncrements` integer IDs, not UUIDs — meaning **order creation, dispute filing, RFQ category selection, recurring-order creation, and payment webhook processing would all reject every real request with a 422**. Fixed all five to `'integer'`.
- [x] **Critical gap (found this session):** the "Négociations" dashboard page and `services/negotiations.ts` have called `/negotiations` since early in this branch, but no route/controller/model/table for negotiations ever existed on the backend — every request 404'd. Added `negotiations` migration, `Negotiation` model, `NegotiationController` (index/store/updateStatus), and routes, mirroring the existing RFQ/recurring-order patterns. Frontend service rewritten with a typed `normalizeNegotiation` (raw snake_case → camelCase), matching the `Rfq`/`RfqBid` normalization pattern already in use.
- [x] Re-enabled full ESLint enforcement in `next build` (was `ignoreDuringBuilds: true`).
